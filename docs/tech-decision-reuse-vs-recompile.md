# 技术决策：复用多看系统 vs 上游重新编译（2026-11-19 评估）

> 用户问题：目前复用多看系统与重新编译之间的差别，会不会更贴合目前系统，收益更高。
> 结论先行：**现状（双变体混合）已是收益最优解**——渲染/UI 层自编译、网络层复用多看 libcurl，
> 两者各取所得。复用是过渡态而非终态，自编译不省 TLS 栈这个大坑。维持现状，附失效预案。

---

## 一、当前系统的复用/自编实况（不是二选一，已经混合）

| 层 | 路线 | 真机状态 |
|---|---|---|
| fb/eink 设备层 | **自研 C**（ABI=多看反汇编定性 + K4Refresh 双机验证知识） | ✅ DK-0 |
| LuaJIT VM | **自编译**（上游 2.1，LUAJIT_DISABLE_JIT，-m32 host） | ✅ DK-1 |
| freetype 渲染 | **自编译**（上游 2.13.2 最小核心） | ✅ DK-1 step2 |
| 网络层 TLS | **复用**（多看 libcurl.so.4.3.0 = curl7.29 + OpenSSL1.0.1e 内嵌，动态变体） | ✅ DK-2（登录/书架/401 全通） |
| 字体数据 | **复用**（多看固件字体 wqy-microhei 等，NOTICE 标注） | ✅ DK-1 |
| 协议/业务 | **自研+插件移植**（protocol/shard/cookie 纯 Lua——插件是协议兼容层，非多看二进制） | ✅ DK-2 |
| 架构模式 | **复用**（单进程 fb 持有者/量化/刷新策略——知识复用） | 全程 |

## 二、逐维度对比（网络层是真正的决策点）

| 维度 | 复用多看 libcurl（动态变体） | 上游自编译 OpenSSL3+curl（静态） |
|---|---|---|
| 开发成本 | **零编译**，1 小时打通（已发生） | 预计 2-4h 交叉静态编译 + 冒烟风险（3.x 在 2.6.31/armv7 无先例） |
| 运行时部署 | 3MB exe + 1.9MB lib（分体，rpath） | 单文件静态（+curl/ssl 约 10MB+） |
| 版本老化 | **curl7.29/OpenSSL1.0.1e（2013 EOL）**：无 TLS1.3、部分新曲线缺失；baidu rc=60 已是 CA 老化预兆 | 2024 版本，长期可控 |
| 安全 | 已知 CVE 群（个人设备+单一域风险可接受，原则上差） | 新版 CVE 面小 |
| 可调试性 | 黑盒（多看编译产物无源码） | 全源码可调 |
| 设备移植 | .so 绑定 K4 glibc 2.12.1；K5 需另配 | 静态跨设备直接拷 |
| 失效模式 | weread 服务端哪天强制 TLS1.3 → **突然全断且无法自救**（只能届时再自编） | 主动可控 |

## 三、结论

1. **网络层：继续复用，直到它断**（触发条件：weread 域 TLS 握手失败），符合"先做起来后续优化"铁律。
   **失效预案（runbook）**：届时按本仓既有配方（`-L~/k4-sysroot/lib` + `-l:精确名` + 静态 CFLAGS）
   交叉编译 OpenSSL3+curl 静态链入静态变体，删除 libcurl 部署件。预计半天内完成。
2. **UI/渲染层：自编译已胜出**——freetype 2.13.2 自编已完成且稳定，多看 libfreetype 2.5.0（2014）
   无切换收益；多看没有 LuaJIT，无复用选项。
3. **多看自有组件（KindleApp/libdkkernel/libkss）不在复用甜点区**：闭源 stripped C++ 大件，
   无头文件无接口，逆向成本 >> 收益（判死项维持）。复用的甜点区=**OSS 成品运行库**（curl/ssl/字体数据）。
4. **"更贴合目前系统"的直接回答**：复用不会更贴合（它带来 glibc 2.12.1 锁定、EABI4/5 边界、
   部署分体三个耦合），自编译不会更快（TLS 栈是唯一大头，已用复用绕过）。**双变体现状=两路线优势交集**，
   静态变体是独立迭代基线，动态变体是"带网络的生产形态"。

## 四、维护纪律

- libcurl 部署件版本/来源已 NOTICE 标注；每次 TLS 冒烟（--net-smoke）即复用健康检查。
- weread 域 TLS 握手失败 = 触发自编译预案的唯一信号（勿提前优化）。
- 若做 K5 移植：优先静态变体（零 .so 依赖），动态变体的 lib 需按设备重评。
